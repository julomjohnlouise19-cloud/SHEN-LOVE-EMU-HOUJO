# Decisions

- D-001 — The uploaded source ends at §4.8; absent economy, UI recipes and phase specifications use explicit conservative defaults rather than invented source requirements.
- D-002 — No /design reference images exist. Use cream paper, peach/lime/lilac accents, ink outlines, hand-drawn inline SVG mascots and generous whitespace for the requested kawaii scrapbook style.
- D-003 — No framework or production dependencies. Vite/TypeScript, ESLint/typescript-eslint, Prettier, Vitest/fast-check and Playwright/axe are free development-only dependencies required by the brief. tsx runs shared TypeScript validation scripts without a second rule implementation.
- D-004 — Local demo data is shared on one browser/origin, with per-tab sessions. Real classroom rewards require school verification and a server; never imply client storage is secure.
- D-005 — Default economy: 3/5/7 merits per correct easy/medium/hard answer, +1 per three-answer combo, 120 daily play-merit cap; correct/attempt XP 12/3, level every 120 XP. Daily spin and quest rewards use separate one-time claims.
- D-006 — Four implementation phases stand in for absent §15. Validate the current bank in early phases and enforce all 972 questions at the content gate.
- D-007 — Self-host the Latin subsets of Google Fonts Fredoka and DM Sans (OFL licenses included) using free Fontsource packages. This removes network font failures and preserves the intended typography offline.
- D-008 — Run TypeScript scripts with `node --import tsx` because the tsx CLI’s IPC socket is unavailable inside the command sandbox; compilation and behavior are unchanged.
- D-009 — Undo is limited to the latest transaction, with a revision check, so restoring an inverse cannot overwrite someone else’s newer progress, stock or purchases.
- D-010 — The 972-card static pool is authored from 324 reviewed concept records with distinct recall, application and evidence prompts. Fixed calculation cards and explicit evidence tables strengthen Hard; the 19 seeded calculators remain separate from this minimum. A science-term allowlist lives in glossary.json.
- D-011 — Precache the production shell, local fonts and static branch chunks after initial load. Cached same-origin resources ignore Vary when matched because preview servers can vary headers between module and precache requests. No cross-origin requests or remote API data are cached.
- D-012 — True/false questions have two choices; the four-choice minimum applies to multiple-choice and diagram/data choice questions. Their answer slots still participate in deck-bias checks.
- D-013 — UI actions for real school supplies remain local demonstration records until a teacher verifies collection; no backend or outbound notification service was supplied or added.
- D-014 — Publish the static app through GitHub Pages at the repository path. VITE_BASE_PATH controls built asset URLs, service-worker scope and precache paths; development defaults to the root path. Verify both root and repository-path builds before upload.
- D-015 — The Pages workflow uses the official GitHub Actions pinned to verified release commits, tests the app before uploading dist, and grants Pages/OIDC write permissions only to the deploy job. GitHub Pages must use the GitHub Actions source in repository settings.
- D-016 — The entry HTML contains a styled startup panel, an embedded SVG favicon and a direct online-lab link before JavaScript runs. This also provides a useful destination when the source HTML is opened from Downloads or JavaScript is disabled, without requiring Vite to transform the favicon path. Normal startup replaces this panel without duplicating it.
- D-017 — Use verified Node 24 Pages actions (configure-pages v6.0.0, upload-pages-artifact v5.0.0 and deploy-pages v5.0.1) on ubuntu-24.04. These remove the observed deprecated Node 20 action warnings and avoid the announced ubuntu-latest image migration during deployment.
- D-018 — First-time and signed-out visitors enter a separate welcome hub. Sign in, create account and guest exploration are explicit choices. Existing valid sessions continue; logging out ends the current tab's session without creating another guest session or deleting saved profiles/progress.
- D-019 — Show a Log out control in the application header and profile, with a confirmation dialog. Remove private views/dialogs on logout, revocation or expiry, including browser Back/restore. Preserve local deck/challenge return paths through entry; never use an external URL as a return destination. A failed storage write still clears the current tab's credential and reports the limitation.
- D-020 — Use “The Cozy Science Lab” as the full website name. Prepare the user-supplied Gun-ob High School seal as a transparent website asset, retaining its wording and school imagery. Use one reusable brand component across desktop/mobile pages and dialog headers; include the asset in offline caching and the favicon.
- D-021 — Focus experience improvements on cross-branch topic discovery, a dashboard resume action for the current user's unfinished run, visible offline guidance and mobile controls. Keep existing accounts, saved progress, science content, economy and logout behavior intact.
- D-022 — Use the official, free @supabase/supabase-js runtime client for the static Vite/GitHub Pages frontend. Enable cloud mode explicitly with VITE_BACKEND_MODE=supabase and public project settings. Reject private keys at build time; do not use or commit the private credential pasted into chat. The owner must revoke that exposed credential.
- D-023 — First backend milestone: Supabase email authentication, Auth-linked profiles, immutable server-graded quiz records, durable idempotent uploads and teacher reports. Keep browser practice, notebook, merits, inventory and real-item claims as local demos. Cloud roles are assigned only through owner-run SQL, never by signup metadata or browser state. Existing local records are preserved and are not silently attributed to a new cloud account.

- D-024 — Cloud accounts use Supabase Auth UUIDs and verified database profiles, separately from old local accounts and guest practice. Save a finished run and its upload job atomically; the server checks the expected owner and deduplicates retries. Cloud logout clears the shared browser Auth session across tabs while retaining pending uploads for the same owner. Teacher report responses stay in page memory.

- D-025 — The owner authorized publication of the connected website. Require Supabase mode and check the real database at the start of the Pages workflow; missing repository settings must fail deployment instead of publishing a successful local demo. Local development and controlled browser tests keep their explicit demo/cloud modes.

- D-026 — GitHub reported an invalid backend-mode repository value during the authorized publication. The production workflow now selects Supabase directly, so only the public project URL and publishable key need owner configuration. This removes a redundant mode switch; local development and demo/cloud tests retain their explicit modes.

- D-027 — Science Arcade uses nine distinct four-choice science cards across three progressive levels (20/16/12 seconds by default). Correct shots earn score and round coins; wrong shots lose a bounded amount without negative balances. Two darts per card, one-second reload, and one extra-time/extra-dart purchase per card prevent spam. Arcade coins fund round power-ups; saved class credits use a separate server ledger. Guest games/rankings remain on the device; signed-in scores are computed from server-owned sessions.
- D-028 — Profile uploads are normalized to small square WebP images and stored in a private owned folder. Only the owner and teachers can read them. Signed image URLs stay in memory, outside backups. Existing preset avatars remain available.
- D-029 — Teacher Studio uses server-checked, idempotent, audited commands and optimistic versions for student profiles/credit adjustments, stock/pricing, collection/cancellation, question edits and learning/game settings. Preserve original quiz scores; teacher annotations add feedback. Class wallets start from configured starter credits instead of trusting old browser balances; awards and stock reservations are transactional. Teacher role assignment stays owner-controlled.
- D-030 — Use product labels such as Saved records, Class credits and Teacher studio throughout the website. Keep service names in developer configuration/documentation only. Refresh shared styling, authentication and transitions while retaining school identity, keyboard support, small-screen layouts and reduced-motion behavior.
- D-031 — Email sending limits are provider settings, separate from database capacity. Add persisted request cooldowns and clear recovery without claiming a quota can be raised by SQL. Keep email confirmation and provide owner instructions for a verified production email sender; never test by emailing real users or request private SMTP credentials in chat.
- D-032 — Preserve numbered question revisions when teachers edit cards. Queued and in-progress quizzes submit the revision they saw; legacy submissions mean revision zero. Retries with an omitted or explicit zero revision are equivalent. The upgrade retains original versions, teacher edits, wallets and stock on rerun. Block deployment until the real backend reports classroom platform 2.

- D-033 — Use coordinated Meadow, Aurora and Sunset palettes with high-contrast text, subject accents, reduced-motion transitions and per-account appearance preferences. Redesign the profile around identity, progress, appearance and account actions. Keep school branding visible.
- D-034 — Back controls name a deterministic in-app destination instead of using browser history. Add shared breadcrumbs and a visible dialog return action so deep links and phones remain predictable.
- D-035 — Record cleanup means filtered views, auditable archive/restore and integrity checks. Preserve original scores, balances and evidence. Use indexed, paginated server queries, bounded bulk commands, request deduplication and reasoned audit history; archived games leave rankings until restored.
- D-036 — Teachers may manage other active accounts' teacher access through a server-checked audited command. Prevent changing one's own teaching access and removing the last active teacher. Owner SQL remains the recovery path; Auth credentials and infrastructure settings stay in the project dashboard.
- D-037 — Platform 3 adds record organization and personal preferences without rewriting earlier records. Existing v2 APIs and UI flows remain compatible; advanced tools activate on platform 3; D-038 describes the compatible rollout. Provide a short existing-project SQL upgrade while retaining complete fresh setup scripts.
- D-038 — The user's repeated priority is fast, working email login. Publish the compatible authentication/design improvements on platform 2 while enabling advanced record-care/delegation tools only after platform 3 is present. The live readiness gate still requires the existing working backend. Report the installed version clearly; do not block the login fix on a separate owner-only schema step or claim new database features are activated before that step.
- D-039 — The owner's screenshot shows a Google settings-page URL in SMTP Host; Gmail requires smtp.gmail.com instead. Website recovery must distinguish a failed email request from an accepted one, keep non-password signup details, allow confirmed-account login and explicit guest practice, and reserve the existing email cooldown atomically before network requests. Never bypass confirmation or claim SMTP delivery is repaired by a frontend change. Keep private sender credentials in the owner's dashboard; do not send real email during automated checks.
- D-040 — Treat the latest request as implementation followed by simple owner instructions. Repair post-login entry using verified account identity and safe, explicit destinations. When a recreated server account reuses a cached email, retain the old identity's local data separately; never transfer its private notes/progress to the new account. Stop silently accepting an invalid account-session envelope.
- D-041 — Retire only Science Arcade/shooting from the active website, including its rankings/history, teacher controls and promotional copy. Preserve the daily spinning wheel, local practice leaderboard, quizzes, profiles, rewards, shop and teacher features. Redirect legacy arcade links to learning/class reports. Preserve historical database tables, credit evidence and upgrade compatibility; no destructive migration or owner SQL is needed. Improve the retained wheel's theme, availability, saved reward feedback and science/notebook follow-up without changing rewards or the one-spin-per-day rule. Add useful learning progress and curated interactive science while keeping reduced-motion support.
- D-042 — Capture a validated requested destination before asynchronous sign-in starts. A session-triggered render may already leave the welcome hub while login finishes; reading its next parameter again at that point can overwrite the correct destination. Both the renderer and completed form must resolve to the same captured destination, with the normal student or teacher fallback.
- D-043 — Show a nonblocking, skippable account guide once per user/role/version, retaining incoming destinations and keeping it replayable. Use large destination-labelled return actions and sticky dialog save/error controls. Preserve Daily spin and the retired shooting-game decision.
- D-044 — Questions are original lab teaching materials. Cite relevant curriculum and publisher/science-agency references as supporting concepts, without inventing quotations, publication dates or claims of exact provenance. Identify constructed tables/calculations and teacher revisions explicitly. Keep references readable offline while external reading links need connectivity.
- D-045 — Suggestions are private to their author and active teachers. Use validated bounded text, idempotent requests, daily limits, versioned teacher status/replies and audit history. Preserve local-demo behavior and account-specific drafts. A separate additive SQL upgrade activates live classroom delivery; never mark a local draft as delivered or bypass database authorization.
- D-046 — The teacher stock form omitted category from its request although the database requires it. Fix the actual payload, enforce the same validation in fixtures, and verify unchecked visibility as well as stock updates. A committed edit must not be reported as failed solely because refreshing secondary totals failed.
- D-047 — Treat mobile stability as functional coverage of phone portrait, short landscape and tablet layouts. Use readable form text, generous touch targets, safe-area spacing and bounded scrolling without disabling browser zoom or changing account, reward, stock or database rules. Preserve the retained daily wheel and science references.
- D-048 — The phone navigation drawer behaves as a labelled modal: provide its own Close control, contain keyboard focus, pause background interaction/scrolling and restore the menu trigger on dismissal. Offer guide and notifications in the drawer when their header controls are hidden. Adapt management/record tables into labelled rows on narrow screens while retaining their table semantics, selection and actions.
- D-049 — Enable Playwright's GitHub reporter alongside its readable test list in Actions, and annotate isolated database exceptions before rethrowing. Failed checks must report the specific assertion or database error through GitHub annotations, rather than only an exit code. Preserve every scenario, assertion and failure exit; local browser checks retain the list reporter. This also permits diagnosis when the cloud workspace cannot fetch the separate Actions log host.
- D-050 — Probe the isolated PostgreSQL container over its loopback TCP connection. The official image starts a temporary Unix-socket-only initialization server and restarts it; a socket readiness check can pass during that temporary phase. Wait for the final server without changing database assertions or accessing the real classroom database.
- D-051 — Sources must remain useful when a publisher site is unavailable or a mobile browser blocks new tabs. Use explicit publisher/document labels, ordinary same-tab reading links, copyable citations and lab-authored topic reading within the website. Keep the original authorship distinction: local learning notes are not a copy of the official curriculum or textbook. Replace the generic DepEd page with the Science curriculum document, and report external link checks without treating a cloud-proxy denial as a publisher error.
- D-052 — Signup requires an explicit unchecked agreement to versioned classroom terms and its privacy notice. Reading the terms does not accept them. Record version and acceptance time in signup metadata (and a separate local-demo record), preserve current form details, and never infer acceptance for older accounts.
- D-053 — Teacher profile views use existing authorized student rows/photos immediately, with an additive teacher-only RPC for email, biography, theme, agreement metadata and aggregate learning data. Never expose credentials or device-only notebook contents. An installed capability flag controls the enhanced view without breaking the current backend.
- D-054 — “Ban user” means disabling a student's classroom account through the existing server-enforced active flag. Require a confirmation/reason, offer restoration and keep records, credits and reservations. Preserve teacher-account protections. An account rejected as inactive is returned to sign-in; network failures do not trigger a ban logout.
- D-055 — Default pickup instructions name the Grade 10 SSC classroom and require a teacher to verify the claim code. Keep pickup location as optional classroom metadata in the existing settings JSON, separate from core reward rules, so current authorized settings APIs work. Show confirmations and durable pending-reservation reminders from existing server orders; do not create email or browser-push notifications.
- D-056 — A verified recovery session supersedes an older per-tab logout marker. Keep a short-lived, tab-scoped recovery marker, revalidate it with Auth after refresh, and require the same verified account before changing a password. A query flag alone never grants recovery. Password reset must remain available if classroom data is temporarily unavailable; preserve existing data and email cooldowns.
